🔗JOINs: Unir Tablas Relacionadas

JOIN permite combinar filas de dos o más tablas basándose en una columna relacionada

¿Por qué necesitamos JOINs?

  • 📦 Los datos están distribuidos en múltiples tablas (normalización)
  • 🔑 Las tablas se relacionan mediante claves foráneas
  • 📊 Necesitamos combinar información de diferentes tablas en una sola consulta

Ejemplo: Unir la tabla "pelicula" con "categoria" para ver el nombre de la categoría en lugar de solo su ID

🔗Tipos de JOINs

INNER JOIN

✅ Solo registros que coinciden en ambas tablas

LEFT JOIN

✅ Todos los de la tabla izquierda + coincidencias

También existen RIGHT JOIN y FULL OUTER JOIN, pero INNER y LEFT son los más usados

🔗INNER JOIN - Explicación

INNER JOIN: Devuelve solo las filas que tienen coincidencias en AMBAS tablas

Sintaxis:

SELECT columnas
FROM tabla_a
INNER JOIN tabla_b ON tabla_a.clave = tabla_b.clave;

📋 Ejemplo práctico:

Tabla: pelicula

pelicula_id titulo categoria_id
1Matrix3
2Toy Story1
3Titanic5
4Sin CatNULL

Tabla: categoria

1Animación

5Romance

⚠️ "Sin Cat" y "Sin Películas" NO aparecerán en el resultado (no hay coincidencias)

✅INNER JOIN - Resultado

SELECT p.titulo, c.nombre AS categoria 
FROM pelicula p
INNER JOIN categoria c ON p.categoria_id = c.categoria_id;

📊 Resultado:

titulo categoria
MatrixCiencia Ficción
Toy StoryAnimación

✅ Solo 3 filas (las que tienen coincidencias en ambas tablas)

Alias: p para pelicula, c para categoria (más legible)
ON: Define la condición de unión (qué columnas relacionar)

⬅️LEFT JOIN - Explicación

LEFT JOIN: Devuelve TODAS las filas de la tabla izquierda + las coincidencias de la derecha (NULL si no hay coincidencia)

Sintaxis:

SELECT columnas
FROM tabla_a
LEFT JOIN tabla_b ON tabla_a.clave = tabla_b.clave;

📋 Mismo ejemplo con LEFT JOIN:

SELECT p.titulo, c.nombre AS categoria 
FROM pelicula p
LEFT JOIN categoria c ON p.categoria_id = c.categoria_id;
titulo categoria
MatrixCiencia Ficción
Toy StoryAnimación
TitanicRomance
Sin CatNULL

✅ 4 filas - todas las películas (incluso "Sin Cat" con NULL)

🤔¿Cuándo usar cada JOIN?

⭕ INNER JOIN

  • ✅ Cuando solo quieres datos completos
  • ✅ Ejemplo: "Películas CON categoría"
  • ✅ Ejemplo: "Alquileres con cliente válido"
  • ✅ Es el más restrictivo (menos filas)

⬅️ LEFT JOIN

  • ✅ Cuando quieres todo de la izquierda
  • ✅ Ejemplo: "Todas las películas (con o sin categoría)"
  • ✅ Ejemplo: "Todos los clientes (alquilaron o no)"
  • ✅ Permite detectar datos faltantes (NULL)

💡 Regla práctica: Si dices "TODOS los X..." probablemente necesitas LEFT JOIN

🎬JOIN con Múltiples Tablas

Podemos unir más de 2 tablas en una sola consulta 

-- ¿Qué películas alquiló cada cliente?
SELECT 
  c.nombre,
  c.apellido,
  p.titulo,
  a.fecha_alquiler,
  a.precio_pagado
FROM alquiler a
INNER JOIN cliente c ON a.cliente_id = c.cliente_id
INNER JOIN pelicula p ON a.pelicula_id = p.pelicula_id
ORDER BY a.fecha_alquiler DESC
LIMIT 5;

💪Ejercicio: Películas por Actor

Objetivo: Listar todos los actores con sus películas

Tablas involucradas:

actor
actor_id, nombre, apellido
pelicula_actor
actor_id, pelicula_id
pelicula
pelicula_id, titulo 
SELECT 
  a.nombre,
  a.apellido,
  p.titulo
FROM actor a

🛡️Integridad Referencial

Asegura que las relaciones entre tablas sean válidas

Reglas:

  • ✅ No puedes insertar un alquiler con cliente_id = 999 si el cliente 999 no existe
  • ✅ No puedes borrar un cliente si tiene alquileres asociados (sin antes borrar los alquileres)
  • ✅ La base de datos garantiza consistencia de datos

Ventaja: La base de datos protege tus datos automáticamente

🎯Normalización de Bases de Datos

Normalización: Proceso de organizar datos para evitar redundancia y mejorar la integridad

¿Por qué normalizar?

  • ❌ Sin normalización: Datos duplicados, difícil de mantener, inconsistencias
  • ✅ Con normalización: Sin redundancia, fácil actualización, datos consistentes

Formas Normales (FN):

  • 1FN: Cada columna tiene un solo valor (valores atómicos, no listas)
  • 2FN: Cumple 1FN + cada columna depende completamente de la clave primaria
  • 3FN: Cumple 2FN + no hay dependencias transitivas (columnas que dependen de otras columnas no clave)

💡 La mayoría de las bases de datos bien diseñadas están en 3FN

❌Tabla NO Normalizada (Violación de 1FN)

pedido_id cliente email productos precios
1Juan Pérezjuan@email.comLaptop, Mouse800, 20
2Juan Pérezjuan@email.comTeclado50
3María Lópezmaria@email.comMonitor, HDMI200, 15

  • Violación 1FN: Columnas "productos" y "precios" contienen listas (no son valores atómicos)
  • Redundancia: Datos de "Juan Pérez" repetidos 2 veces
  • Anomalía de actualización: Si Juan cambia su email, hay que modificarlo en 2 lugares
  • Anomalía de inserción: No puedes agregar un cliente sin un pedido
  • Anomalía de eliminación: Si borras el pedido 3, pierdes la información de María

🔬Propiedades ACID

ACID: Garantías que ofrecen las bases de datos relacionales para asegurar la confiabilidad de las transacciones

A - Atomicidad

"Todo o nada" - Si una parte falla, todo se revierte

Ejemplo: Transferencia bancaria de 100€

  • 1️⃣ Restar 100€ de cuenta A
  • 2️⃣ Sumar 100€ a cuenta B
  • ⚠️ Si falla el paso 2, se revierte el paso 1
  • ✅ No se pierde dinero

C - Consistencia

Reglas siempre válidas - Los datos cumplen todas las restricciones

Ejemplo: Alquilar una película

  • ✅ El cliente_id debe existir en tabla cliente
  • ✅ El pelicula_id debe existir en tabla pelicula
  • ✅ El precio_pagado debe ser > 0
  • ⛔ No puedes insertar datos inválidos

I - Aislamiento

Transacciones independientes - No se interfieren entre sí

Ejemplo: Dos usuarios comprando la última entrada

  • 👤 Usuario A: Consulta → 1 entrada disponible
  • 👤 Usuario B: Consulta → 1 entrada disponible
  • ✅ Solo UNO podrá comprarla (locks)
  • ⛔ El otro verá "agotado"

D - Durabilidad

Cambios permanentes - Una vez confirmado, no se pierde

Ejemplo: Confirmar un pedido

  • ✅ Se guarda en disco (no solo en RAM)
  • 💾 Aunque se vaya la luz, el pedido está guardado
  • 🔄 Sistema se recupera automáticamente
  • ✅ Los datos no se pierden nunca

🏗️CREATE TABLE: Crear Tablas

CREATE TABLE: Comando DDL (Data Definition Language) para definir la estructura de una tabla

CREATE TABLE cliente (
    cliente_id SERIAL PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    apellido VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE NOT NULL,
    fecha_registro TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    activo BOOLEAN DEFAULT true
);

📋 Explicación línea por línea:

  • cliente_id SERIAL PRIMARY KEY → ID autoincremental, clave primaria única
  • nombre VARCHAR(100) NOT NULL → Texto hasta 100 caracteres, obligatorio
  • email VARCHAR(150) UNIQUE NOT NULL → Email único, no puede repetirse
  • fecha_registro TIMESTAMP DEFAULT CURRENT_TIMESTAMP → Fecha/hora actual automática
  • activo BOOLEAN DEFAULT true → true/false, por defecto true

💡 SERIAL: Tipo especial que genera IDs automáticamente (1, 2, 3, ...)

➕INSERT: Insertar Datos

INSERT INTO cliente (nombre, apellido, email) 
VALUES ('Juan', 'Pérez', 'juan@email.com');

Insertar múltiples filas:

INSERT INTO cliente (nombre, apellido, email) 
VALUES 
    ('María', 'García', 'maria@email.com'),
    ('Carlos', 'López', 'carlos@email.com'),
    ('Ana', 'Martínez', 'ana@email.com');

No necesitas especificar cliente_id porque es SERIAL (auto-incremento)

✏️UPDATE: Modificar Datos

UPDATE cliente 
SET email = 'nuevo_email@email.com' 
WHERE cliente_id = 1;

⚠️ ¡CUIDADO!

Si olvidas el WHERE, actualizarás TODAS las filas

-- ❌ ESTO CAMBIA TODOS LOS EMAILS
UPDATE cliente SET email = 'mismo@email.com';

🗑️DELETE: Eliminar Datos

DELETE FROM cliente 
WHERE cliente_id = 3;

⚠️ ¡MÁS CUIDADO AÚN!

Si olvidas el WHERE, borrarás TODA la tabla

-- ❌ ESTO BORRA TODOS LOS CLIENTES
DELETE FROM cliente;

Consejo: Primero haz un SELECT con el WHERE para verificar qué vas a eliminar

⚡Índices: Acelerar Consultas

Índice: Estructura de datos que permite encontrar filas rápidamente sin escanear toda la tabla

📖 Similar al índice de un libro: saltas directamente a la página que buscas

🔍 ¿Cómo funcionan?

❌ Sin Índice

Búsqueda secuencial:

WHERE email = 'juan@email.com'

1. Revisa fila 1 ❌
2. Revisa fila 2 ❌
3. Revisa fila 3 ❌
...
999,998. Revisa fila 999,998 ❌
999,999. Revisa fila 999,999 ✅

⏱️ Tiempo: 10 segundos

🐌

✅ Con Índice

Búsqueda optimizada:

WHERE email = 'juan@email.com'

1. Consulta índice (estructura árbol)
2. Salta directamente a la fila ✅

⏱️ Tiempo: 0.001 segundos

🚀

💻 Crear un índice:

-- Índice en columna email para búsquedas rápidas
CREATE INDEX idx_cliente_email ON cliente(email);

-- Ahora esta consulta es MUY rápida:
SELECT * FROM cliente WHERE email = 'juan@email.com';

⚠️ Compromiso: Los índices aceleran SELECT pero ralentizan INSERT/UPDATE (hay que actualizar el índice)

👁️Vistas (Views)

Vista: Consulta SQL guardada como si fuera una tabla virtual (no almacena datos, solo la consulta)

¿Para qué sirven?

  • ✅ Simplificar consultas complejas: Escribes el JOIN una vez, lo usas muchas veces
  • ✅ Seguridad: Ocultar columnas sensibles (contraseñas, datos privados)
  • ✅ Reutilización: Mismo dato en múltiples lugares

📝 Crear una vista:

-- Crear vista con películas + categoría
CREATE VIEW v_peliculas_completas AS
SELECT 
    p.pelicula_id,
    p.titulo,
    p.año_lanzamiento,
    c.nombre AS categoria,
    p.duracion,
    p.precio_alquiler
FROM pelicula p
INNER JOIN categoria c ON p.categoria_id = c.categoria_id;

🔍 Usar la vista (como si fuera una tabla):

-- Consulta simple, pero ejecuta el JOIN internamente
SELECT * FROM v_peliculas_completas 
WHERE categoria = 'Acción' 
ORDER BY año_lanzamiento DESC;

💡 La vista no ocupa espacio (no guarda datos), solo ejecuta la consulta cuando la llamas

💳Transacciones

Transacción: Conjunto de operaciones SQL que se ejecutan como una unidad atómica

Todo se completa exitosamente ✅ o nada se completa ❌

📋 Ejemplo: Transferencia bancaria

✅ Transacción exitosa:

BEGIN; -- Iniciar transacción

-- Paso 1: Restar dinero de cuenta A
UPDATE cuenta 
SET saldo = saldo - 100 
WHERE cliente_id = 1;

-- Paso 2: Sumar dinero a cuenta B
UPDATE cuenta 
SET saldo = saldo + 100 
WHERE cliente_id = 2;

COMMIT; -- ✅ Confirmar cambios
-- Ambas operaciones se guardan

❌ Transacción fallida:

BEGIN; -- Iniciar transacción

-- Paso 1: Restar dinero de cuenta A
UPDATE cuenta 
SET saldo = saldo - 100 
WHERE cliente_id = 1;
-- ✅ Ejecutado

-- Paso 2: Error (cuenta B no existe)
UPDATE cuenta 
SET saldo = saldo + 100 
WHERE cliente_id = 999;
-- ❌ ERROR!

ROLLBACK; -- 🔄 Deshacer TODO
-- El paso 1 se revierte automáticamente
-- No se pierde dinero

✅ Garantía: O se ejecutan TODAS las operaciones, o NINGUNA. No hay estados intermedios.

  • ✅ Usa tipos de datos apropiados

  • ✅ Documenta tu esquema
  • ✅ Crea índices en columnas que se consultan frecuentemente
  • ✅ Usa transacciones para operaciones críticas
